# Post-Mortem: Poison Pill Message Blocks Shipping Partition

## Service Overview

- **Incident date:** 2026-05-21, 09:12-12:20 UTC (3 hours 8 minutes)
- **Affected services:** ShippingService, which consumes `order-events` to create shipments, and OrderService, which produces the events.
- **Impact:** About 1,900 orders on partition 7 of `order-events` had no shipment created for over 3 hours. Other partitions were unaffected. Shipments were delayed by one day for orders that missed the courier cut-off.

## Common Error Signatures

### Deserialization Error Repeating on One Offset

```text
org.apache.kafka.common.errors.RecordDeserializationException: Error deserializing key/value for partition
order-events-7 at offset 884213. If needed, please seek past the record to continue consumption.
Caused by: org.apache.avro.AvroTypeException: Found null, expecting string (field: shipping_address.postal_code)
    at ShippingService.consumer.poll()
```

- **Observed:** The same offset (884213) appeared in the logs thousands of times.
- **Observed:** Lag on partition 7 grew steadily while all other partitions stayed near zero.

## Root Cause Analysis

### Producer Schema Change Without Compatibility Check

An OrderService release made `shipping_address.postal_code` optional to support countries without postal codes, and started sending `null` for it. ShippingService still used the old schema, in which the field is a required string. The schema registry's compatibility mode was set to `NONE`, so the incompatible change was accepted.

### Deserialization Errors Bypassed the Dead Letter Queue

ShippingService had a dead letter queue (`order-events.dlq`), but it was only used for errors raised inside the message handler. Deserialization fails earlier, inside `poll()`, so the consumer retried the same record indefinitely and never moved past it. The record became a "poison pill" for the whole partition.

## Playbook Remediation

### Immediate Mitigation

1. A hotfix of ShippingService wrapped deserialization so failing records are sent to `order-events.dlq` and consumption continues. It was rolled out with:

   ```bash
   kubectl rollout restart deployment/shipping-service -n fulfillment
   kubectl rollout status deployment/shipping-service -n fulfillment
   ```

2. Recovery was tracked until lag on partition 7 returned to zero:

   ```bash
   kafka-consumer-groups --describe --bootstrap-server kafka:9092 --group shipping-service
   ```

3. The 41 records in the DLQ were replayed after ShippingService was updated to the new schema.

### Follow-up Actions

1. Set schema registry compatibility for `order-events` to `BACKWARD`, so producers cannot publish changes that break existing consumers.
2. Route deserialization errors to the DLQ in all consumers, not only handler errors.
3. Alert when a single partition's lag grows for 10 minutes while others stay flat.
