# Post-Mortem: FraudDetectionService Cold Start Causes Cascading Payment Timeouts

## Service Overview

- **Incident date:** 2026-04-02, 12:10-12:33 UTC (23 minutes)
- **Affected services:** PaymentGateway, which calls FraudDetectionService synchronously with a 2000 ms gRPC deadline before every authorization, and FraudDetectionService, which scores each payment with a machine learning model.
- **Impact:** About 7% of payment authorizations failed during the lunchtime peak. Customers saw "payment could not be processed" and some retried, creating duplicate pending orders.

## Common Error Signatures

### Deadline Exceeded in PaymentGateway

```text
grpc._channel._InactiveRpcError: <_InactiveRpcError of RPC that terminated with:
    status = StatusCode.DEADLINE_EXCEEDED
    details = "Deadline Exceeded"
>
    at PaymentGatewayClient.Authorize()
```

- **Observed:** The autoscaler scaled FraudDetectionService from 3 to 8 pods at 12:08.
- **Observed:** Errors came almost entirely from requests routed to the 5 new pods. Their p99 latency was about 6 seconds during their first minutes, while the original pods stayed under 300 ms.

## Root Cause Analysis

### Cold-Start Latency in New Pods

New FraudDetectionService pods load their ML model lazily, on the first scoring request, and the JVM is not yet warmed up. The first requests to each new pod took 4-8 seconds. The readiness probe only checked that the HTTP server was up, so Kubernetes sent traffic to pods that could not yet answer within PaymentGateway's 2000 ms deadline. The timeouts appeared in PaymentGateway, but the cause was the cold pods downstream.

### Synchronous Dependency Without Fallback

PaymentGateway treated any failure of the fraud check as a failed payment, and retried immediately up to 3 times. Retries were often routed to cold pods again and added load during warm-up, which extended the incident.

## Playbook Remediation

### Immediate Mitigation

1. The autoscaler was paused, and the deployment was scaled manually so that warm pods carried the load:

   ```bash
   kubectl scale deployment fraud-detection-service -n risk --replicas=10
   kubectl rollout status deployment/fraud-detection-service -n risk
   ```

2. Errors stopped once all pods had served their first requests, about 4 minutes after the last scale-up.

### Follow-up Actions

1. Load the model at startup, and make the readiness probe pass only after the model is loaded and a few warm-up predictions have run.
2. Set a minimum of 6 replicas during business hours, and scale up earlier based on request rate.
3. Add exponential backoff with jitter to PaymentGateway retries, and propagate the request deadline.
4. Add a fallback in PaymentGateway: when the fraud check times out, approve low-risk payments below a set amount and queue them for asynchronous review.
